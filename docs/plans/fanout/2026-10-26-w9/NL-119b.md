### 3.3 Review fix F-1: remote-edit p95 must not include samples taken while a peer is disconnected
Problem (`load/yjs-mix.ts`): `type_once` puts `token -> t0` in every peer's `unseen`; the observer pushes `t1 - t0` to `remote_samples` whenever the token first shows, even if the sender or the observing peer was down in between (the token only arrives after reconnect, so the sample is the outage length, not the latency).
Change:
- `Editor` gains `epoch: number` (starts 0). Increment it in `onDown` (inside the `e.state !== "up"` guard, where the state becomes `"down"`) **and** at the planned-drop site just before `ws.close(4000)` (so a token typed between `close()` and the `onClose` event is also excluded).
- `unseen` becomes `Map<string, { t0: number; sender: Editor; sender_epoch: number; peer_epoch: number; clean: boolean }>`. In `type_once`, per peer: `clean = e.state === "up" && peer.state === "up"`, `sender_epoch = e.epoch`, `peer_epoch = peer.epoch`.
- At first sighting (the `observeDeep` callback), call the pure `is_clean_sample` (below) with the stored values and the current `{state, epoch}` of sender and peer. Clean goes to `remote_samples`; otherwise to a new `remote_drop_samples` array. Never dropped silently.
- New pure function in `load/yjs-stats.ts`:
```ts
export interface LinkView { sender_up: boolean; peer_up: boolean; sender_epoch: number; peer_epoch: number }
/** A remote-edit sample is clean only if both ends were up when the edit was made and neither dropped before it was seen. */
export function is_clean_sample(at_send: LinkView, at_seen: LinkView): boolean {
  return at_send.sender_up && at_send.peer_up && at_seen.sender_up && at_seen.peer_up
    && at_send.sender_epoch === at_seen.sender_epoch && at_send.peer_epoch === at_seen.peer_epoch;
}
```
- `p95_json` keys: `remote_edit` (clean samples only, ms), `remote_edit_n`, `remote_edit_during_drop` (p95 of the excluded samples, ms; 0 if none), `remote_edit_during_drop_n`. Nothing else in `p95_json` changes. `MixResult.n` still counts tokens sent.
- Not changed (decision, noted in devlog Open items): `stored` samples have the same contamination for a sender that was down when it typed. The ticket and the review asked for remote_edit only; apply the same `is_clean_sample` to `stored` in a follow-up if the 5% drop run shows stored p95 outliers.

### 3.4 Review fix F-2: unacknowledged tokens after the drain timeout make the run incomplete
Problem: after the `drain_ms` wait, tokens still unacknowledged are only reported as `p95_json.unacknowledged`; `incomplete` stays false and `exit_code` is 0, so a run that never got `stored` for its last edits looks clean.
Change in `run_yjs_mix_detailed`:
- Replace the scattered `incomplete = true` assignments with `const mark_incomplete = (reason: string) => { incomplete = true; incomplete_reason ??= reason; }` using reasons `connect_timeout`, `socket_down`, `error` (the `catch`), and the new `unacknowledged_after_drain`.
- Immediately after the drain loop: `if (outstanding() > 0) mark_incomplete("unacknowledged_after_drain");` (only when not already incomplete from a socket problem; `??=` keeps the first reason). Lost-update counting still runs (an unacknowledged token is not "lost", it was never promised).
- `YjsMixDetail` gains `incomplete_reason: string | null`; `p95_json.incomplete_reason` carries it (null when complete). `run_yjs_probe`'s `exit_code` rule is unchanged: `incomplete || lost_updates > 0` gives 1, so F-2 reaches the process exit through §3.2.
- The reload check stays gated on `!incomplete`.
- `load/report.ts` line 106 only: replace the text with `- ${n} socket editors requested; their Yjs figures are in the separate kind=yjs probe_run row (NL-119), not in this report.` (`report.test.ts` asserts nothing on the old wording; run it).
