## 1. Goal and sources

Deliver CON-23 (`listExports`, `createExport`, `downloadExport`): a versioned JSON export of a unit's approved lesson snapshots. A dependent lesson is included only while every lesson it links to is approved. Exporting twice with no change writes nothing. Newly included lessons move `approved → exported` in the same transaction as the insert. Approver only.

## 5. Steps

Design decisions already made (do not reopen):

D1. **Download returns the stored `ExportBundleFile`** (the published schema document), not the OpenAPI `LessonExportFile` envelope. The ticket and CON-23 prose ("a JSON document in the Lesson export schema", validates against `lesson-export.schema.json`, hash equals `payload_hash`) win over the OpenAPI example (R3).

D2. **`generated_at` is deterministic**: the maximum `stored_at` of the included approve snapshots as `toISOString()`, or `"1970-01-01T00:00:00.000Z"` when nothing is included. A wall-clock value would make every export differ and break idempotence. An empty included set is exported like any other payload (it hashes the same each time, so it is idempotent); no extra error code is invented.

D3. **`approved_by` = the approve snapshot's `created_by` (a user id)**, `approved_at` = its `stored_at.toISOString()`. Never a name or email. If `created_by` is null, throw `InvariantViolation`.

D4. **Payload is not stored; `PgExportRepo.payload()` reconstructs it** from `lesson_version` rows named in `lesson_versions_json` (rows are append-only by trigger, so this is faithful; there is no DDL, R2). `payload()` recomputes the hash and throws `InvariantViolation` if it differs from `payload_sha256` (fail closed: never serve a file that does not match its hash). The service builder and the repo reconstruction implement the same record shape (about 15 lines each); the route test's hash equality catches drift.

D5. **Dependants rule is a fixpoint**: a snapshot lesson is held back if any lesson it `waits_on` is not in state `approved`/`exported` OR is itself held back. Held-back `reason` is the constant `"a lesson it links to is not approved"` (the OpenAPI example text); `waits_on` is the blocking lesson id (the screen builds "Lesson 4 waits on Lesson 5").

D6. **Unit reference**: the path param may be a canonical id (`G6.U4`) or a key (`g6-u4`). Resolve via `OutlineRepo.list_units()`: match `u.unit_id === ref || u.unit_id.toLowerCase().replace(".", "-") === ref`. No match: `NOT_FOUND`. All later queries use the canonical `unit_id`.

D7. **Constructor** (positional; DO-4 gave 7, two additive seams are needed, R3): `constructor(versions: LessonVersionRepo, exports: ExportRepo, audit: AuditLog, tx: TxRunner, ids: IdGenerator, clock: Clock, states: LessonStateRepo, graph: LessonGraphRepo, units: Pick<OutlineRepo, "list_units">)`. `clock` is used for nothing but is kept for DO-4 parity (do not remove).

D8. **Role**: the service itself rejects `user.role !== "approver"` with `DomainRefusal("ROLE_FORBIDDEN", "Your role cannot do this.")` at the top of `list`, `create`, `download` (defence in depth behind `with_route`).

D9. **`created_by` in `ExportVersion`** is the user id (no name lookup port exists). Not a defect for this ticket.
