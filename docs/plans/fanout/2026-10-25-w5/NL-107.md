## 4. Design

Scenario harness (`ops/faults/world.ts`): one fresh test DB per scenario (`create_test_db`), seeded as in `make_world`, `StubModelClient` with `on_enter` hook, `WorkerDeps` built with `PgDatabase` from the test DB and `stub_prices()` copied from `apps/worker/test/support/world.ts` (price `stub-model`), settings from `load_worker_settings(env)` with env overrides per scenario (cap, `DRAFT_OUTPUT_TOKEN_CAP`, `TRUNCATION_RETRY_TOKEN_CAP`). The stub run id is `run_id` returned by `RunService.start`; every assertion filters by it (OBS-2).

1. **kill (AC-1).** The worker runs as a **child process** `npx tsx ops/faults/worker-child.ts` (env: `DATABASE_URL` of the scenario DB, a scripts-dir path of stub script options). The child builds `PgDatabase`, `StubModelClient` scripted with `stub-drafts.ts`, `wire_generation`, and `claim_loop.run_until` (it does its own wiring because `apps/worker/src/main.ts` never starts the loop and its `db`/`model_client` are `unbuilt`: seam S-8, see Open items). The parent polls `select count(*) from lesson_job where run_id=$1 and status='ready'` every 25 ms and sends `SIGKILL` when it first reaches **>= 10** (count-based, not time, for AC-8). Before killing it records `in_flight = count(model_call where run_id=$1 and status in ('sent','pending'))` (read the real in-flight status word from `packages/llm/src/recorder.ts`). Then it starts a second child; `ClaimLoop.start()` marks the dead calls lost and requeues. Pass condition: 47 jobs terminal; `select lesson_id, version_number, count(*) from lesson_version where run_id=$1 group by 1,2 having count(*)>1` returns 0 rows (use the real column names: `lesson_version` has `number`, no `version_number`, per `packages/db/migrations/0006_lessons.sql`; the ticket SQL is illustrative, assert on the real columns); no completed `model_call` followed by another call for the same `job_id`+`attempt`; `duplicates_found = 0`; `calls_lost_counted = in_flight`. If `lesson_version` has no `run_id`, join through `lesson_job`.
2. **rate_limit (AC-2).** In-process `drive_until`. Stub function for `GENERATION/*`: the first 8 calls (shared counter) return `{kind:"error", error: new ProviderError("rate_limited", ...)}` (copy the constructor signature from `packages/core/src/errors.ts`), later calls healthy drafts. Pass: all 47 `lesson_job.status='ready'`; no job with reason `rate_limited`; extra `model_call` rows (`status`, `stop_reason`, `retries` show the retries). Run `select count(*) from lesson_job where run_id=$1 and status<>'ready'` = 0.
3. **truncation (AC-3, both variants).** Variant A: lesson `G6.U4.L4`'s first draft call returns `{kind:"text", text:<partial>, stop_reason:"max_tokens"}` and the retry is healthy: that lesson has exactly 2 `model_call` rows and `stub.calls` for it show `max_output_tokens` 32000 then 48000. Variant B: both calls `max_tokens`: lesson ends `generation_failed`, reason `truncated`, exactly 2 calls, no third. Each variant is its own run on its own DB (small run is enough for the variant; use all 47 only if cheap, otherwise scope rows `[8]`; the ticket says "seeded 47-lesson run" for the suite, so use 47 and truncate one lesson).
4. **cap (AC-4).** `cap_usd` below the stub run's total cost: compute the healthy per-lesson cost first (`stub_prices`, stub token counts are `ceil(chars/4)`), set cap about 40% of the 47-lesson total. Pass: `sum(spend_reservation.settled_usd) <= cap_usd`; `run.state='capped'`; remaining jobs not started; no `spend_reservation.status='reserved'`; a lesson capped mid-way is released not paid.

Cases and evidence: `cases()` returns 4 `EvalCase`s with ids `kill`, `rate_limit`, `truncation`, `cap` (`provenance: "synthetic"`, `source: "HP-7"`, `guards`: the invariant text, `input_path`: `ops/faults/scenarios.ts`, `expected`: the numbers above). `score()` runs the scenario and returns `actual` built **from SQL reads after the scenario** (`FaultSuiteReport` fields come from stored rows, not process memory). `truncation.actual` carries both variants. The report front matter (EV-R1) must name git SHA, prompt version, model IDs (the stub's `stub-model`), `n` (47) and `provider_mode: stub`; `EvalRunner` already passes `git_sha`, `prompt_version_id`, `models`; confirm in `evals/src/report.ts` and, if a field is absent from the generated report, put it into `actual`/`expected` and the section text via `SectionInput` (no runner edit). The scenario run id goes into `eval_run.run_id` only if the runner supports it; otherwise it is in `actual_json`.

Determinism (AC-8): fixed kill point by stored-lesson count; `ClaimLoop` concurrency is fixed by `generation_concurrency` in settings, but which exact lesson is in flight at the kill varies, so `actual` records only counts that are invariant (47, 0 duplicates, `calls_lost_counted == in_flight` as a boolean, and the number is **not** printed in the report body). Timestamps and ids stay out of the report body.

Canary (AC-6): put `sk-FAULT-CANARY-001` in the child env as `ANTHROPIC_API_KEY` (and the in-process env), capture the child's stdout/stderr to `ops/faults/out/worker-<scenario>.log`, then assert with `grep -rF` semantics over `evals/reports`, `ops/faults/out`, and `select count(*) from eval_case_result where actual_json::text like '%sk-FAULT-CANARY-001%'` = 0. The runner's `make_leak_guard(env)` already throws if an env secret reaches evidence; it must not fire.

## 5. Risks to build for (not to patch around)

- **Per-lesson stub drafts.** Only `apps/worker/test/fixtures/stub-drafts/wp-1.json` and `wp-2.json` exist (lessons L4, L5; both need the exact rows 8/9). A 47-lesson stub run needs a draft that passes `compile_check` for every lesson. `stub-drafts.ts` must derive one from the request: take the `wp-2.json` draft, rewrite `lesson_id`, front-matter standards and section addresses from the lesson row named in the request (`lesson_of(req)` helper in `world.ts`), and choose lesson types the same way the NL-79 world does. If the gate (`generation_rules` in `wiring/generation.ts`) still rejects some lessons, that is a **failing invariant to report**, not a reason to edit the worker. Allow the stub to answer the repair call from the same fixture. The implementer should try 3 lessons end to end first (about 20 min of work) before building the four scenarios.
- **Fixtures and the restricted folder.** Drafts are synthetic; read nothing from `docs/source/restricted/` (GR-9). The `wf-28-obligations` case for GR-9 asserts no path under `restricted` appears in any `rendered_prompt`, report or log of the run; GR-13 asserts the seeded users are `synthetic: true` and no student data columns exist in the run's rows.
- **Disk.** Four fresh databases plus child processes; `drop()` each in `finally`; no Docker image builds; check `df -h /home` first (about 96% full).
- **Timing.** Use event barriers (poll SQL, count-based), never sleeps as pass conditions (S-16 lesson).
