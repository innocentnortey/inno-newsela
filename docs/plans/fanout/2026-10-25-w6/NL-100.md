## 4. Seed design (`con-11/seed-lessons.ts`)

Runs after `stack.seed()` (reference data, standards, three demo users) against `DATABASE_URL`. Compiles the WP-1 stub draft with `compile_lesson` (`packages/core/src/compile/`, NL-18; `compile-draft.test.ts` shows the call and fixture) and stores it through the document-store port (`PgLessonDocStore`, NL-36), then writes versions with `PgLessonRepo` in one tx each. It needs a unit and a confirmed outline version with a row for `G6.U4.L4` so the evidence pane's outline row segments exist (reuse the shape in `packages/db/src/repos/outlines.int.test.ts` or `seed_world`; copy, do not import test files into the app). Lessons seeded (all ids are real `G6.U4.L<n>` lessons of one unit so the board and path forms work):
1. `G6.U4.L4` WP-1: state `draft`, `generated` v1 with provenance, plus a non-adopted `candidate` v2.
2. A `submitted` lesson: `generated` v1, `submit` snapshot (v2), then live `lesson_doc` edited afterwards by direct SQL (AC-4).
3. An `approved` lesson: `generated`, `submit`, `approve`; a fourth lesson carries `reopen` so SCR-16 shows generated, candidate (not adopted), submit, approval, reopen in one list. Human-made versions (submit/approve/reopen) must name `derived_from_version_id` and inherit `outline_row_hash`, `prompt_version_id`, `schema_version`, `run_id` (CON-19); the existing repo sets these, assert not assume.
4. A lesson whose stored `schema_version` is 99 (UPDATE on `lesson_doc.schema_version` and derived json by SQL; keep the original JSON to prove "stored JSON unchanged").
5. A lesson with a stored node of unknown type (SQL edit of `derived_json`).
6. A lesson for AC-6 with the two markup strings in a paragraph (both in `lesson_doc` and in a `submit` snapshot, so SCR-9 and SCR-16 and the JSON body all carry it).
7. A version whose provenance lacks a field (SQL `provenance = provenance - 'prompt_version_id'` on one row) for the "Missing" case. If the table forbids it (NOT NULL or check), the spec uses the closest legal omission and the devlog says which.
`seed()` returns `{ lessons: {wp1, submitted, approved, reopened, schema99, badnode, markup, missing}, versionIds }` read back through `db()` queries; specs never hard-code ids.
