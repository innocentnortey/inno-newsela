**Step 2. `packages/db/src/repos/run-progress.ts`: `PgRunProgressReader implements RunProgressReader`**, `constructor(deps: PgRepoDeps)` (import type from `./audit.ts`). `progress_rows` does ONE `this.db.with_tx(async (tx) => {...})` containing exactly three `tx.query` calls, all SELECT, in this order (invariant: 3 statements, no writes):
1. Run + spend (return `null` early if no row):
```sql
SELECT r.*,
  (SELECT coalesce(sum(settled_usd),0)::text FROM spend_reservation s WHERE s.run_id = r.id) AS settled_usd,
  (SELECT coalesce(sum(CASE WHEN s.status = 'reserved' THEN s.reserved_usd ELSE 0 END),0)::text FROM spend_reservation s WHERE s.run_id = r.id) AS reserved_usd
FROM run r WHERE r.id = $1
```
Map the run row exactly as `map_run` in `packages/db/src/repos/runs.ts` does (copy the field mapping; it is private there; do not edit that file). Money to `new Decimal(text)`.
2. Jobs:
```sql
SELECT j.id, j.run_id, j.kind, j.lesson_id, j.status, j.tile_state, j.attempt, j.queued_at, j.started_at, j.finished_at,
  j.failure_reasons_json, j.brakes_fired, j.repairs, j.truncation_retries, j.retries, j.calls_lost, j.cost_usd,
  l.title AS lesson_title, l.number AS lesson_number
FROM lesson_job j LEFT JOIN lesson l ON l.id = j.lesson_id
WHERE j.run_id = $1 ORDER BY j.queued_at, j.id
```
Map to `ProgressJobRow` (`failure_reasons: r.failure_reasons_json ?? []`, `cost_usd: new Decimal(r.cost_usd)`, other fields as in `map_job` in runs.ts).
3. Queued ahead (claim order is fair-share; this is the FIFO approximation, state it in a code comment):
```sql
WITH mine AS (SELECT queued_at, id FROM lesson_job WHERE run_id = $1 AND status = 'queued' ORDER BY queued_at, id LIMIT 1)
SELECT count(*)::int AS n
FROM lesson_job j JOIN run r ON r.id = j.run_id CROSS JOIN mine
WHERE j.run_id <> $1 AND j.status = 'queued' AND r.state IN ('planning','running')
  AND (j.kind <> 'lesson' OR r.plan_stored_at IS NOT NULL)
  AND (j.queued_at, j.id) < (mine.queued_at, mine.id)
```
(`mine` empty → `n` = 0.) **Step 5. `control`**:
```ts
async control(user: RequestUser, run_id: RunId, req: RunControlRequest): Promise<RunControlResult>
```
1. `user.role !== "author"` → `throw new DomainRefusal("ROLE_FORBIDDEN", "Only authors can control a run.")` (before touching a repo).
2. `const out = await this.tx.with_tx(async (tx) => { ... })`, in this order (invariant protected: row lock first so two clicks serialise; a refusal throws inside the tx so nothing is written):
   a. `run = await this.runs.lock_for_update(run_id, tx)` (NOT_FOUND if unknown).
   b. `d = decide_run_control(run.state, req.action)`; `!d.allowed` → `throw new DomainRefusal("INVALID_TRANSITION", "That action does not fit the run's state.", { state: run.state })`.
   c. `requeued: string[] = []`.
      - `cancel` (`d.cancel_jobs`): `await this.queue.cancel_run(run_id, "cancelled", tx)`; then `await this.runs.set_state(run_id, "cancelled", null, tx)`. In-flight jobs are not touched (the worker stops at its next node via `is_cancelled`). No lesson row is created or deleted.
      - `retry_failed` (`d.requeue_failed`): BEFORE requeueing read `failed = (await this.queue.jobs_for_run(run_id)).filter(j => j.status === "generation_failed")`; `await this.queue.requeue_failed(run_id, tx)`; `requeued = failed.map(j => j.lesson_id).filter((x): x is string => x !== null)`; `await this.runs.set_state(run_id, "running", null, tx)`.
      - `resume`: if `run.paused_check === "unit_plan"` (plan call failed) call `await this.queue.requeue_failed(run_id, tx)` (re-queues the failed `unit_plan` job; `requeued` stays `[]` because it has no lesson id); then `await this.runs.set_state(run_id, "running", null, tx)`. Use `d.to_state` for the state argument in all three branches, never a literal.

## 8. Risks and requests

- **R1 new read port (seam the design lacks).** AC-4 caps the progress read at 3 queries, but run + spend + titles + `queued_ahead` need more than 3 with the existing ports (no port can answer `queued_ahead` or lesson titles). Decision (ticket > DO-4): add the small additive `RunProgressReader` port and `PgRunProgressReader` (new files, no edit to an existing port). `RunService` takes it via the optional 13th constructor parameter so the DO-4 12-argument shape and NL-27's fakes stay valid. Integrator may fold it into DO-4 later.
- **R2 missing index (request to the integrator).** `lesson_job` has no `(run_id)` index (only `lesson_job_one_candidate` in `0004_runs.sql`), and DO-3 says all DDL is NL-08's and no other ticket writes a migration. AC-4's "touches the `lesson_job(run_id)` index" cannot be proven. Request: a `CHG` plus migration `create index lesson_job_run_id_idx on lesson_job (run_id, queued_at)` (a 47-row read is fine without it at demo scale, but the claim query and this read both filter on `run_id`). This ticket adds no migration; in `indexed_read_no_writes` leave an `it.todo("progress read uses the lesson_job(run_id) index")` and say so in the report.
- **R3 trace-incomplete field is not in the contract.** `RunSummary` (zod and OpenAPI) has no flag. Decision: the service returns `RunSummary & { trace_incomplete: boolean }` and the route sends it as an additive property (clients ignoring unknown keys are unaffected; `with_route` does not validate responses). Request: a `CHG-N` adding `trace_incomplete` (boolean) to `RunSummary`; no schema or OpenAPI edit here.
- **R4 `concurrency_cap` source.** `GENERATION_CONCURRENCY` lives only in worker settings. Wiring reads the env var directly with default and max 6 (the setting's own default and range); a web-settings field would edit shared config. Request: expose it on `WebSettings` in a later config change.
- **R5 `attempts`, `updated_at`, plan-state choices.** `attempts` = the job's stored claim count `attempt`; `updated_at` = newest stored timestamp (no clock); a `failed` plan on a run no longer `paused` reads as `planning` (after a resume). All follow the contracts' wording and are recorded in the devlog.
- **R6 NOTIFY** goes through `extras.notify` (a post-commit `pg_notify` in wiring) because the ports are opaque about SQL; workers also poll, so it only affects latency.
- Collisions: none by ownership (W4 collision row gives `run-service.ts`, `wiring/runs.ts`, `runs/[runId]/**` to NL-78). Touching `wiring-stubs.test.ts` (NL-06's) is a one-row delete; NL-53/54 will make the same delete for their own rows, so a merge conflict there is a "keep both deletions" resolution.
