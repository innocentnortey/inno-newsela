`src/pool.ts`
```ts
export class PgDatabase {
  constructor(settings: SharedSettings, pool_max: number, acquire_timeout_ms: number, pool_name: PoolName = "web");
  with_tx<T>(fn: TxFunction<T>, advisory_lock?: string | null): Promise<T>;
  ping(): Promise<boolean>;   // SELECT 1 on a short-lived acquire; any error (incl. PoolExhausted) -> false, never throws
  close(): Promise<void>;     // pool.end()
}
```
Implementation: `new pg.Pool({ connectionString: settings.database_url.reveal(), max: pool_max, connectionTimeoutMillis: acquire_timeout_ms })`;
also `pool.on("error", () => {})` so an idle-client error does not crash the process. `with_tx` times `pool.connect()` with `performance.now()`;
pg's timeout error (message starts `timeout exceeded when trying to connect`) -> `throw new PoolExhausted(pool_name, Math.max(acquire_timeout_ms, Math.round(elapsed)))`
(so `waited_ms >= 200` is exact). Any other connect error rethrows unchanged. `client.release()` in `finally` (pass the error to `release(err)` when the rollback itself failed). Never log the connection string.

`src/migrate.ts`
```ts
export interface MigrationReport { applied: string[]; already_applied: number }
export class MigrationError extends Error { readonly migration_id: string; readonly problem: string;
  constructor(migration_id: string, problem: string) } // message names the file
export interface MigrateOptions { dir?: string; build_id?: string; service?: string } // defaults: ../migrations next to this file via new URL("../migrations/", import.meta.url); build_id = resolve_build_id(process.env, git_short_sha); service "migrate"
export async function run_migrations(db: PgDatabase, opts?: MigrateOptions): Promise<MigrationReport>;
```
Algorithm (one outer `db.with_tx` is NOT used; each file gets its own transaction):
1. List `*.sql` in `dir`, sorted by name (plain string sort; names are zero-padded). `id` = file name (e.g. `0001_identity.sql`).
2. Take `pg_advisory_xact_lock(hashtext('migrate'))` inside each file's tx so two processes starting together serialise; inside the lock re-read applied set.
3. Applied set: `SELECT to_regclass('schema_migrations')`; null -> empty set, else `SELECT id, checksum FROM schema_migrations`.
4. For every file: checksum = sha256 hex of the raw file bytes (`node:crypto`). If applied with a different checksum -> `throw new MigrationError(id, "checksum mismatch: file changed after it was applied")` **before applying anything further** (check all already-applied files first, in order, then apply the pending ones). Same checksum -> counts toward `already_applied`.
5. Pending file: in its own `with_tx`: `tx.query(sql)` (multi-statement file; no parameters), then `INSERT INTO schema_migrations (id, checksum, applied_at) VALUES ($1,$2,now())`. Any throw rolls the whole file back; wrap non-MigrationError failures as `MigrationError(id, err.message)`; earlier files stay recorded.
6. `ops_event` is created by `0012`, so files `0000`..`0011` cannot write their event in their own tx. Rule: if `to_regclass('ops_event')` is non-null inside the tx, write `record_ops_event(tx, {kind:"migration_applied", service, build_id, details:{migration_id:id, checksum}})` in the same tx; otherwise keep `{id, checksum, at}` in memory and, in the same tx as the file that creates `ops_event` (0012), insert the deferred events first (their `at` = their own apply time, in order), then 0012's own event. On entry, backfill: for every `schema_migrations` row with no `ops_event` of kind `migration_applied` whose `details_json->>'migration_id'` equals it, insert one (covers a crash after 0012 rolled back and a later re-run). Net result on an empty DB: 13 `schema_migrations` rows and 13 `ops_event` rows.
7. Return `{ applied: [ids newly applied, in order], already_applied: <count of previously applied> }`; a second run returns `{applied: [], already_applied: 13}`.

## 6. Triggers and the view (in the file of the table they guard)

`0008_review.sql`:
- `create function reject_mutation() returns trigger language plpgsql as $$ begin raise exception 'append-only: %', tg_table_name; end $$;` then `create trigger review_event_append_only before update or delete on review_event for each row execute function reject_mutation();` likewise `audit_event`. (Message format `append-only: review_event`.)
- `create view audit_log_v as select at, 'review_event'::text as source, lesson_id, actor_id, u.name as actor_name, 'lesson.transition'::text as action, from_state, to_state, content_hash as version_hash, reason from review_event left join app_user u on u.id = actor_id union all select at, 'audit_event', (case when target_kind='lesson' then target_id end), actor_id, u.name, action, null::text, null::text, version_hash, reason from audit_event left join app_user u on u.id = actor_id` wrapped as `select * from (...) t order by at`. `audit_event` has no `lesson_id` column; the view derives it as shown (target_kind `lesson`) **and** `details_json->>'lesson_id'` as fallback: `coalesce(case when target_kind='lesson' then target_id end, details_json->>'lesson_id')`. AC-10 inserts the audit row with `target_kind 'lesson'`.
- `lesson_metrics` trigger (`reject_mutation`, before update or delete) goes in `0009_metrics.sql` (reuses the function from 0008).
`0006_lessons.sql` is applied before 0008, so the **lesson_version trigger function is defined in 0006** itself:
```sql
create function lesson_version_guard() returns trigger language plpgsql as $$
begin
  if tg_op = 'DELETE' then raise exception 'append-only: lesson_version'; end if;
  if new.content_hash is distinct from old.content_hash or new.state_vector is distinct from old.state_vector
     or new.lesson_json is distinct from old.lesson_json or new.draft_json is distinct from old.draft_json
     or new.provenance_json is distinct from old.provenance_json
     or new.dependency_record_json is distinct from old.dependency_record_json
     or (old.adopted and not new.adopted)
  then raise exception 'append-only: lesson_version'; end if;
  return new;
end $$;
create trigger lesson_version_guard before update or delete on lesson_version for each row execute function lesson_version_guard();
```
(`false -> true` passes; `true -> false` raises; a second `false -> true` is impossible after the first). `reject_mutation` is therefore defined in `0008`, used by `0009` (order is fine).
No view anywhere reads `heartbeat`, `review_session` or `lesson_metrics`.
