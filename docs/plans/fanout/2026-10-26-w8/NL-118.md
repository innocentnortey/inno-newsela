### 3.2 Pure schedule (`load/http-mix.ts`, no server needed)

```ts
export type VuRole = "reviewer" | "poller" | "actor";
export type EventKind = "open" | "heartbeat" | "poll" | "act" | "page";
export interface ScheduleEvent { t_ms: number; vu: string; role: VuRole; kind: EventKind; n: number }  // n = per-VU tick counter
export interface MixShape { users: number; ramp_s: number; plateau_s: number; ramp_down_s: number }
export const SHARES = { reviewer: 0.7, poller: 0.2 } as const;           // actor = the rest (10%)
export const PERIOD_S = { heartbeat: 15, poll: 2, act: 10, page: 30 } as const;
export function vu_id(i: number): string;                                // "vu-001"
export function split_roles(users: number): { reviewers: number; pollers: number; actors: number };  // round(0.7u), round(0.2u), rest
export function build_schedule(shape: MixShape, seed?: number): ScheduleEvent[];  // sorted by t_ms; deterministic (mulberry32, default seed 118)
export function rate_in_window(events: ScheduleEvent[], kind: EventKind, from_s: number, to_s: number): number;  // events per second
export async function run_http_mix(opts: SpikeOptions, deps: MixDeps): Promise<HttpMixResult>;
```

Rules: VU `i` of `users` starts at `ramp_s * i / users` and stops at `ramp_s + plateau_s + ramp_down_s * (i / users)`; `ramp_down_s` defaults to 120 (CLI `--ramp-down-s`); `build_schedule` ticks each kind at its period with a per-VU random phase and +-5% jitter per tick (mean rate stays exact). Reviewers: one `open` at their start then `heartbeat` every 15 s; pollers: `poll` every 2 s; actors: `act` every 10 s; **everyone** `page` every 30 s. A `page` event is role-mapped at run time: reviewer -> `GET /api/lessons/{id}` (class `lesson_open`), poller and actor -> `GET` of the HTML board page (class `page`). Because the plateau window sums over VUs, at 200 users the plateau rates are: heartbeat 140/15 = 9.33/s, poll 40/2 = 20/s, act 20/10 = 2/s, page 200/30 = 6.67/s.

Request mapping in `run_http_mix` (open loop: dispatch at `t_ms`, never wait for the previous response; abort a request at 30 s as a socket-level failure):
- `open`/reviewer `page`: `GET /api/lessons/{lessonId}` -> class `lesson_open`. Lesson ids round-robin over the discovered lessons.
- `heartbeat`: `POST /api/lessons/{lessonId}/heartbeats` with a stable per-VU `tab_id` = the VU id, `focused:true, visible:true, last_input_at = sent_at - 5 s`, `version_id` from the lesson read (fall back to the `current_version_id` of the board row) -> class `heartbeat`.
- `poll`: VUs with an even index poll `GET /api/units/{unit}/board` (class `board`), odd index poll `GET /api/runs/{runId}/progress` (class `progress`) when a run exists, else board. Class `poll` = every poll tick (board or progress), so `p95_ms.poll` covers both; `p95_ms.board` is the board subset.
- `act` (actors; first half are authors, second half approvers): reads `GET /api/units`, `GET /api/prompt-versions`, `GET /api/units/{unit}/board` rotating; **the one safe write class**: an approver `act` tick 1 time in 4 sends `POST .../heartbeats` (class `act_write`, stored, synthetic, excluded from minutes; authors never send heartbeats, CON-20). It is tagged separately so the `heartbeat` rate in AC-1 is the reviewers' alone. The script never calls any other write route (no lesson content, no transition, no run start).
- `page` for poller/actor: `GET /units/{unit_key}/board` HTML (class `page`).

Discovery before the clock starts (`discover(base_url, cookies)`): `GET /api/units` -> pick the `--unit` (flag; default first unit that has lessons) -> `GET /api/units/{id}/board` -> lesson ids (cap 50) and `unit_key`; `latest_run.run_id` if present. If there are no lessons: exit 2 with "nothing to probe: seed lessons first" before any load. If there is no run, progress polling falls back to board and the report says "progress poll skipped: no run" (not an error).

### 3.3 Statistics (`load/stats.ts`, pure)

```ts
export interface Sample { t_ms: number; ms: number; ok: boolean }
export function percentile(values: number[], p: number): number;                 // nearest-rank: sorted[ceil(p/100*n)-1]; p95 of 1..100 = 95; empty -> NaN is NOT allowed: throw
export function error_rate(failed: number, total: number): number;             // fraction; 3 of 300 = 0.01; total 0 -> 0
export function window_p95s(samples: Sample[], window_s: number): { start_s: number; p95_ms: number; n: number }[];  // ok samples only
export function baseline_p95(windows: ..., first_s: number): number | null;   // p95 over samples in the first window(s) of the ramp (load <= ~25%); null when < 5 samples
export function recovery_s(windows: { start_s: number; p95_ms: number }[], baseline: number, plateau_end_s: number, tol?: number /* 0.10 */): number | null;
```
`recovery_s` = seconds after `plateau_end_s` at which the first window starts from which this and every later window is `<= baseline * (1 + tol)`; `null` when it never settles (report prints "not recovered"); a window already settled at plateau end gives 0. M-23 = the max over `lesson_open`, `board`, `poll`. Windows default 1 s in tests, 5 s in the run. Latency samples exclude failed requests (a `SERVICE_BUSY` 503 or any 5xx or socket error is an error, never a slow success: AC-5).

Error accounting: `error_rate = (5xx + socket drops/timeouts) / (requests + sessions)` where `sessions` = the 3 sign-ins. 4xx are counted separately as `client_errors` (script or seed bug), excluded from latency and from `error_rate`, listed in the report; the int test asserts it is 0. `n` = total completed requests (sessions not included). `lost_updates` = 0 (HTTP half has no edits).

Event-loop lag: `perf_hooks.monitorEventLoopDelay({resolution: 10})` enabled for the run; `event_loop_lag_p95_ms = h.percentile(95) / 1e6`. The report states that **server-side event-loop lag is not measured here**.
DB connections: a 1 s `setInterval` runs `select count(*)::int from pg_stat_activity where datname = current_database()` through `PgDatabase` (own pool max 1, isolated from the app's pool); `max_db_connections` = max seen.

`ProbeRunRecord` assembled by `run_spike`: `kind:"http"`, `users`, `duration_s` (actual elapsed whole seconds from ramp start to last response), `machine = \`${cores} cores, ${mem_gb} GB RAM, ${os.platform()}\``, `provider_mode:"stub"`, `p95_ms` = `{lesson_open, board, poll, heartbeat, page, recovery_s}` (numbers or null; `recovery_s` lives in `p95_json` so M-23 stays computable from the row without a schema change; `remote_edit` and `stored` are NL-119's), `error_rate`, `lost_updates:0`, `event_loop_lag_p95_ms`, `max_db_connections`, `n`, `probe_run_id = new_id("pr")`.

### 3.4 `run_spike` and the CLI

```ts
export interface SpikeDeps {
  evidence: EvidenceRepo; db_url: string; password: string; emails: Record<VuRole-to-account, string>;
  provider_mode: "stub" | "real"; out_dir: string; request_log: string; git_sha: string; now: () => Date;
  ramp_down_s?: number; unit?: string; fetch?: typeof fetch;
}
export async function run_spike(opts: SpikeOptions, deps?: SpikeDeps): Promise<ProbeRunRecord>;
```
`run_spike(opts)` with no `deps` builds them from the environment (the CLI path). Order: (1) refuse `provider_mode !== "stub"` with `ProbeRefusal` before any fetch; refuse a `base_url` host that is not `localhost`/`127.0.0.1`/`::1` unless `--allow-remote` (keeps Render and public hosts safe); `opts.socket_editors > 0` is ignored by this half and recorded in the report (NL-119 owns it); (2) sign in once per account (author, reviewer, approver; three `POST /api/session`, `Origin: <base_url origin>`), VUs of a role share that role's cookie (200 password hashes would be a startup spike unrelated to the mix); (3) discover; (4) start lag + DB samplers; (5) run the schedule; (6) stop samplers, compute stats; (7) `evidence.insert_probe_run(record)`; (8) write the request log JSONL (`{t_ms, vu, class, method, path, status, ms}` per request, header `x-probe-run-id` and `x-probe-vu` sent on every request, never cookies or passwords) and the report; (9) print ONE JSON line on stdout `{"probe_run_id":"pr_...","report_path":"...","request_log":"..."}` and exit 0 (missed targets are reported, not a failure).

`load/cli.ts`: `parse_args(argv, env): CliConfig`. Flags: `--users` (int>=1, default 200), `--ramp-s` (120), `--plateau-s` (900), `--ramp-down-s` (120), `--base-url` (env `LOAD_BASE_URL`, default `http://127.0.0.1:3000`), `--database-url` (env `DATABASE_URL`, required, local `evidence` DB of the stack under test), `--password-env` (name of the env var holding the seed password, default `LOAD_PROBE_PASSWORD`; never a CLI value), `--unit`, `--out-dir` (default `evals/reports`), `--request-log` (default `<os.tmpdir()>/ls-load/<probe_run_id>.requests.jsonl`), `--provider stub|real` (default `stub`), `--allow-remote`. Exit codes: 2 for a refusal or bad usage (message on stderr, no request sent, no DB write), 1 for a runtime failure, 0 ok. The existing hard-coded `await run_spike({users:200,...})` stub block is replaced by `main(process.argv.slice(2), process.env)`; keep the `pathToFileURL` entry guard.

Targets (capacity doc, *Performance targets* and *Recovery criteria*): `lesson_open p95 < 1500 ms`, `poll p95 < 300 ms` (board and progress; `board` shown too), `error_rate < 0.005`, `recovery_s <= 120` (null = missed).
