## 1. Goal and sources

Three deliverables, all additive (new files only, no production source edits):

**A. Real lifecycle boundary tests.** The unit test `apps/worker/src/wiring/check-parity.test.ts` builds three loader contexts and calls rule helpers; its "submission" branch is `CHECK_RULES.flatMap(r => r.run(...))`, not the live submission service. It stays as it is (unit test, must stay green). New integration tests drive the **actual services** on the test Postgres: generation (`wire_generation` claim loop, `StoreNode` writes the compiled lesson) -> background check (`CheckJobRunner` from `wire_checks`) -> reviewer edit (web `SlotService` / `IssueService` -> collab `apply_edit`; free-text typing through the collab store `LessonPersistence.store`) with a content-hash and version change -> submit (`TransitionService` -> collab `lock_and_snapshot`) -> approve (`ApproveService`) -> export (`ExportService`). Cases: valid supported content, missing rationale, forged source card, bogus standard tag on an empty-focus row added by a reviewer edit, missing required slot vs open slot vs source supplied vs confirmation pending vs approved, removed teaching evidence after an edit. Assertions: the same input gives the same core finding in generation, background, submit and approve; the lifecycle adds only explicitly defined human-work blockers; "generation-ready", "awaiting human work" and "approved" are distinct states.

**B. Queue/version compatibility inventory** (`ops/queue-compat.ts` + runbook): lists active (`running`) AND `queued` generation jobs by pinned `prompt_version_id` / `locked_hash` against a locked layer (disk by default), so a worker replacement finishes old-version jobs with a matching artifact or uses an explicit supported transition. Never silently repins or cancels. `LockedLayerMismatch` is expected when an old pin meets new locked files. Includes the test of the inventory query.

**C. Isolated real-stack e2e runner** (`ops/e2e-real-stack.sh`): one script, serial, private copy of the candidate tree (own `.next`, own stack files), own database, correct env, and a run record that states the exact commit, a dirty-file hash and the run's validity.

`INVENTORY_SQL` (parameterless, the first statement of the transaction is `SET TRANSACTION READ ONLY`):
```sql
SELECT j.id AS job_id, j.run_id, j.kind, j.status, j.lesson_id, j.queued_at, j.lease_until,
       r.state AS run_state, r.prompt_version_id, p.number AS prompt_number, p.locked_hash AS pinned_locked_hash
  FROM lesson_job j
  JOIN run r ON r.id = j.run_id
  LEFT JOIN prompt_version p ON p.id = r.prompt_version_id
 WHERE j.status IN ('queued', 'running')
 ORDER BY r.prompt_version_id, j.queued_at, j.id
```
The pin is `run.prompt_version_id` (`packages/db/migrations/0004_runs.sql`; the claim SQL returns `r.prompt_version_id` and the renderer asserts `locked_hash(disk) === prompt_version.locked_hash`, `packages/prompts/src/render.ts` lines 65 to 68). `claimable_now = run_state IN ('planning','running')` (the claim SQL `active` CTE in `packages/db/src/repos/job-queue.ts` lines 39 to 44 only reads those runs); a queued job of a `paused` or `capped` run is a **latent** backlog that a resume or retry can make live, so it is listed with `claimable_now false` and counted in `queued_in_unclaimable_runs`, never dropped. `retryable_failed` (only `--include-failed`): `status = 'generation_failed'` in runs whose state is `partial` (these are requeued by the run-control `retry_failed` action; `packages/core/src/lifecycle/run-machine.ts` lines 70 to 80), same join.
