### Story
US-36 — As Innocent I need honest page-speed numbers at the 200-user spike (PD-33: 500 users a day, 200 at once). This ticket builds the HTTP load script and proves it measures correctly with a small run; NL-127 runs the real 200-user spike on the VPS.

### What to build
Build the HTTP half of the S14 capacity probe (A20; DO-4 §9 `SpikeOptions`, `run_spike`; DO-3 §4 `load/spike.ts`).

- Files: `load/spike.ts` (fills NL-49's shell), `load/http-mix.ts` (virtual-user behaviours and the schedule), `load/stats.ts` (percentiles, windows, recovery), tests. Command: `npm run load:spike -- --users 200 --ramp-s 120 --plateau-s 900` (NL-127 runs it; here a small run proves it).
- **The mix** (`docs/design/capacity-and-workload.md` *Workload assumptions*), as shares of `users`: 70% reviewers open a lesson (CON-11) then send a heartbeat (CON-20) every 15 s; 20% poll the unit board (CON-9) or run progress (CON-6) every 2 s; 10% authors and approvers act about once per 10 s (a mix of reads and one safe write class); everyone loads a page about once per 30 s. Burst shape: 2-minute ramp, 15-minute plateau, 2-minute ramp down.
- **Safety of the data:** virtual users sign in as seeded synthetic-flagged accounts (`synthetic` is seed-only, CON-1); their heartbeats are stored but excluded from minutes (CON-20); the script never writes lesson content or a transition, so demo data and the north-star numbers stay clean. If the seed script (NL-82) has no synthetic probe accounts, that is a gap raised to the batch merge agent, not an edit to `ops/seed.ts`.
- Provider stubbed: `provider_mode` is `stub` only and the script refuses `real`.
- Output: one `ProbeRunRecord` (`kind: "http"`, `users`, `duration_s`, `machine`, `provider_mode`, `p95_ms` for `lesson_open`, `board`, `poll`, `error_rate` (5xx + socket drops ÷ requests + sessions), `max_db_connections` sampled each second from `pg_stat_activity`, `event_loop_lag_p95_ms` = the load script's own lag, `n`) through `EvidenceRepo.insert_probe_run`. Server-side event-loop lag is not measured by this ticket; the report says so. Recovery time (M-23) = time from plateau end until each p95 window is back within 10% of the pre-spike window.
- Must not: touch lesson content, run against a real provider, or edit any route.
