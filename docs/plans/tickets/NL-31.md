### Story
US-9 — As an outline author (P-2), I need one plan for the whole unit — a line for every teaching day with what it hands forward — written and stored before any lesson is drafted, so that lessons are written against one consistent plan and I can read it first.

### What to build
**Module:** `apps/worker/src/generation/unit-plan-job.ts` — `UnitPlanJob` (DO-4 §6), constructor `(paid, renderer, runs, outlines, prompts, settings)`. `run(job: ClaimedJob) → UnitPlanOutcome{run_id, stored, entries, model_call_id, failure}`.
1. **Input.** `runs.get(run_id)` (scope, outline version), `outlines.rows(outline_version_id)` filtered to the run's scope rows (all lesson and flex-day rows for scope `all`), the outline's unit rules from `outlines.row_context(ov, first_lesson_id, runs.pinned_choices(run_id)).unit_rules`, and `outlines.links(ov)` (the links the run copied at start; computed by code, never by the model, HP-1). `renderer.render_unit_plan(UnitPlanPromptInput{run_id, prompt = prompts.get(job.prompt_version_id), rows, unit_rules, links})`.
2. **Call.** `recorder.checkpoint(job_id, "unit_plan", 1)` first: a completed stored output is validated and used with **no new call**. Otherwise one `PaidCaller.call` (`purpose "unit_plan"`, alias `GENERATION`, `output_mode "schema_enforced"` because `UnitPlanDraft` compiles, SP-1; `max_output_tokens DRAFT_OUTPUT_TOKEN_CAP` since DO-3 §7 has no separate plan cap, `ctx.attempt 1`, `user_id = job.started_by`).
3. **Validate (Zod `UnitPlanDraft`, then code).** Exactly one entry per teaching day in scope, each `lesson_id` in scope, no duplicates, `day` ascending. A failure triggers **at most one repair**: because DO-4 defines no plan-repair renderer, the repair is one more `render_unit_plan` call with the same input (`purpose "repair"`, ordinal 1; reported as a DO-4 gap). Still invalid → `runs.mark_plan_failed(run_id)` (run `paused`, `paused_check "unit_plan"`; Resume re-queues the job, CON-7) and `failure = schema_invalid`.
4. **Store.** Valid → `runs.store_unit_plan(run_id, plan, model_call_id)` (sets `plan_stored_at`, `unit_plan.state stored`, run `running` in one transaction, NL-27), which is what makes lesson jobs claimable (R-8, NL-28). The `lesson_link` rows already sit in the run's plan row from `startRun`; the model's hand-forward text stays advisory.
5. **Refusals.** `SpendRefused` → `runs.mark_capped(run_id, cap)`, `failure = capped`, no call row. A surviving `ProviderError` → `mark_plan_failed`, `failure` = its kind (`rate_limited`, `timeout`, `provider_error`).
Must not: store anything before validation passes; let a lesson job start first (the gate is `plan_stored_at`); write `lesson` rows; create jobs; edit `claim-loop.ts` or `run-finalizer.ts` (NL-30).
