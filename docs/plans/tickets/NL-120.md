### Story
US-36 — the build's numbers need their causes, not only their counts. Zero-to-hero §9 and GP-21/GP-51 say no tuning change lands without a named failure type; this ticket produces the named failure types (`FT-N`) from what the full run (NL-112) actually did, so NL-128…130 each change one thing against one `FT-N`.

### What to build
Read about 20 stored traces from the NL-112 run to their **first failure only**, file each under an `FT-N` written from what was seen, and write the table the experiments rest on. Output lives in `docs/testing/error-analysis/` (new; this ticket owns it).

**Method (DO-5 *Failure categories*; `docs/design/eval-plan.md`):**
1. **Pick the traces (about 20 of 47).** All lessons that ended `generation_failed`; all with a blocking issue after the repair; every lesson whose first draft needed the repair; then fill to about 20 with a seeded-random draw (seed written in the file) across lesson types. List the chosen `lesson_job` ids and why each was picked.
2. **Read each trace to its first failure.** From the stored rows (`model_call` rendered prompt and raw output, `issue`, `lesson_version`) via the operator's read-only SQL or the run summary (CON-21); never the restricted folder. Stop at the first thing that went wrong; do not catalogue later damage. Record: lesson id, step that first failed, one quoted line of evidence, the starting category (FC-1…FC-14) it falls under.
3. **Write `FT-N`s from what was seen.** Rename, split or merge FC-n as the traces demand; each `FT-N` has a one-sentence definition, the count, an example trace id, and where the fix would live (prompt layer, schema, check, compiler, code). Operational failures (429, timeout, cap) are not quality failures (GP-58): list them apart.
4. **Models × failures table.** Rows `FT-N`, columns the models and prompt versions the traces ran on (all `claude-sonnet-5-5` prompt v1 unless the run shows otherwise; the table says so rather than inventing columns).
5. **Recommend, do not run.** End with at most three candidate experiments, each: one `FT-N`, one variable, the expected effect, cost to score on the frozen set. These become NL-128/129/130; slots without a warranted `FT-N` are closed unused (slice plan open item 7).
6. **Human gate.** Innocent reviews the taxonomy and the candidate list (`gate::human`). Under PD-32 (his standing authorization) Claude's recommendation stands if he has not answered when the next dependent ticket is ready; the issue then records "adopted under PD-32 fallback, not reviewed by Innocent" and the dev log says the same. Unreviewed traces never become eval cases (DO-5 *Case provenance*): promotion to `promoted-trace` happens only after his review.

Lane guard (`ticket-lanes`): before committing, `git diff --name-only` must list no file that code or tests read (source, tests, schemas, migrations, prompts, settings, lockfiles, fixtures, CI); if it does, stop, relabel the ticket `lane::build-loop` and report. Commit straight to `main` (factory mode, PD-34).
