### Story
US-36 — As a content lead judging whether to trust this tool, I need … the page-speed probe, and, if built, the editor load script …, so that every number in the demo has its *n* and a source. The brief asks that "loading/editing of lessons should be performant and be able to handle staff of 20+ reviewers"; Innocent set the bar at 500 users a day with a 200-user spike (PD-33), so this is the run that shows whether the stack holds it and says honestly where it does not.

### What to build
Run NL-118's load probe against the full Compose stack on the VPS and publish the result. **Run and report; do not tune.** A missed target is reported with the scale-path step that would fix it (`capacity-and-workload.md` *Scale path*), not fixed here.

**Pre-flight.** `df -h /home` shows enough free disk for logs and the database (the VPS disk is nearly full; stop and tell Innocent if under 3 GB free); `nproc` and `free -g` recorded for the report header; the stack is the committed Compose config with Postgres unpublished; the seeded unit from NL-112 is loaded so lessons are real size (~3,300 words); the **model provider is stubbed** (the worker's stub adapter, NL-79): no real model call is made, so spend is $0.

**The run.** `npm run load:spike` (NL-118): 200 virtual users in the DO capacity mix (70% reading/editing a lesson with a heartbeat every 15 s, 20% on polling screens at 1 poll / 2 s, 10% authors/approvers, page loads about every 30 s), a **2-minute ramp, a 15-minute plateau and a 2-minute ramp down** (`capacity-and-workload.md` *Workload assumptions*), with a generation run in flight on the stub so the worker and the polls compete as in real use. It writes a `probe_run` row (WF-29: p95s, error rate, connection counts, event-loop lag, *n*, machine, stub stated) and `evals/reports/load-<date>.md`. If NL-119 (the Yjs socket script, cut #1) landed, run `npm run load:spike -- --yjs` as well (WF-30: remote-edit p95, stored p95, lost updates, reconnect time, store transaction time); if it was cut, the report says "Yjs latency was not measured".

**Recovery.** After the plateau, keep sampling for 5 minutes and report the time until p95s return to the pre-spike level.

Lane guard (`ticket-lanes`): before committing, `git diff --name-only` must list no file that code or tests read (source, tests, schemas, migrations, prompts, settings, lockfiles, fixtures, CI); if it does, stop, relabel the ticket `lane::build-loop` and report. Commit straight to `main` (factory mode, PD-34).
