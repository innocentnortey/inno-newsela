### Story
US-15 — I edit together with others and know my edits are stored; US-22 — I am told when an edit is refused because the lesson froze. NL-63 built the live editor against a mock collaboration server and NL-80 built the real one with its session auth, write guard and store; this ticket proves two real sessions co-edit one lesson, a reload keeps the edits, an unauthenticated socket is refused and nothing persists after a lock.

### What to build
- Specs under `apps/web/e2e/integration/con-12/` on `startStack({ web: true, collab: true })` with the collab server **in-process** (built from `wire_collab_server`, NL-80) so the test can call `FrozenDocs.freeze(lesson_id)` to model the Submit lock mid-session without NL-106. - During its run this ticket alone may fix `apps/web/src/editor/**` (NL-63's files) and the collab auth/guard/ack glue it finds wrong, each fix in the dev log.
- Must not: write lesson content over HTTP, edit the Submit freeze command (NL-106), or weaken the reviewer-only write rule.
