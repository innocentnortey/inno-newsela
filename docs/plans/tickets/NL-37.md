### Story
US-16 — As a reviewer (P-1), I need the issue list to refresh after each save and to tell me when a newer save is still being checked, so that I know at once whether an edit broke a rule and never trust a stale list. This ticket is the queue that makes checks run once per stored hash and the table that keeps issues tied to the hash they were computed on.

### What to build
**Module:** `packages/db/src/repos/check-queue.ts` — `PgCheckQueue implements CheckQueue` and `PgIssueRepo implements IssueRepo` (DO-4 §3.4, §3.5), both from `PgRepo_ctor`; tables `check_job` (`0007_checks.sql`) and `issue` (NL-08). Runs at the check worker (NL-81), the store (NL-36), the issue service (NL-45) and Approve/Submit (NL-53, NL-106) use it.
**PgCheckQueue.**
- `enqueue(lesson_id, content_hash, store_id, tx)`: joins the caller's transaction; coalesced — at most one `queued` row per lesson (partial unique index): a newer hash **replaces** the queued row's `content_hash`/`store_id` (and `enqueued_at` stays the oldest), an already running row is left alone and a fresh queued row follows it; issues `NOTIFY check_job` after the surrounding commit.
- `claim(lease_ms)`: `FOR UPDATE SKIP LOCKED`, oldest queued first, also reclaiming a `running` row whose `lease_until` has lapsed; sets `claimed_at`, `lease_until`; returns `ClaimedCheck{lesson_id, content_hash, store_id, lease_until}` or null. `finish(check)`: marks that row `done` with `finished_at` (never touches a newer queued row).
- `pending_for(lesson_id)` → `PendingCheckState{pending, newest_queued_hash, latest_stored_hash, latest_stored_at}`: `pending` is true while a queued or running `check_job` exists for a hash newer than the lesson's `checked_hash`; `latest_stored_*` are read from `lesson_doc` (read only).
**PgIssueRepo.** Issues are keyed to the content hash they were computed on.
- `replace_for_hash(lesson_id, content_hash, findings, tx)`: inserts one `issue` row per `CheckFinding` (`iss_…`, level, kind, message, address, span_anchor, related_lesson_id, code); for each finding whose **(kind, address, code)** matches an earlier resolved issue of the lesson it copies the resolution forward (`resolved_by`, `resolution_reason`, `resolved_at`, `cleared_by "resolution"`); a finding with a different key gets no carried resolution; earlier-hash issues that no longer appear are marked `cleared_by "fix"`. Returns `IssueSet{lesson_id, checked_hash, checked_at, issues}`.
- `current(lesson_id)` → the issue set of the newest checked hash (empty set with null hash before the first check); `get(issue_id)`; `resolve(r: NewResolution, tx)` sets `resolved_by`, `resolution_reason`, `resolved_at`, `cleared_by "resolution"` on an unresolved issue and returns the row (an already-resolved issue is returned unchanged); `resolutions_for(lesson_id)` → the latest resolved row per (kind, address, code) across all hashes (what `merge_resolutions` matches at Submit and Approve, G-14); `counts_by_lesson(unit_id)` → unresolved `blocking`, `confirmation` and `advisory` counts on each lesson's newest checked hash.
Must not: run any check; read lesson content; write `lesson_doc`, `alignment_link` or any other table; decide whether a kind is resolvable (the services do, CON-13); edit `lesson-docs.ts` (NL-36) or `lessons.ts` (NL-42).

### Acceptance criteria
- [ ] AC-1 [invariant] Coalescing: three `enqueue` calls for one lesson with hashes H1, H2, H3 before any claim leave one `queued` row carrying H3 and its store id; after a claim of that row, a fourth enqueue (H4) adds a new `queued` row beside the running one (WF-10) — verify: `npx vitest run packages/db/src/repos/check-queue.int.test.ts -t coalesce_to_newest` (Postgres 16 test container) — evidence: row dump after each step — covers: R-28, OBS-4, M-26
- [ ] AC-2 [invariant] `enqueue` is part of the caller's transaction: with the caller rolling back, no `check_job` row remains; committed, a `NOTIFY check_job` is received by a listening client — verify: `npx vitest run packages/db/src/repos/check-queue.int.test.ts -t enqueue_joins_tx_and_notifies` — evidence: 2 cases — covers: R-28, OBS-4
- [ ] AC-3 [invariant] Two concurrent `claim(lease_ms)` calls on one queued row: exactly one gets a `ClaimedCheck`, the other null; a running row with a lapsed lease is reclaimed by the next `claim` and one with a live lease is not; `finish` marks only the claimed row `done` and leaves a newer queued row untouched — verify: `npx vitest run packages/db/src/repos/check-queue.int.test.ts -t claim_skip_locked_and_lease` — evidence: 3 cases — covers: R-28, OBS-8
- [ ] AC-4 [invariant] `pending_for`: with a stored hash newer than the last checked hash it returns `pending true`, `newest_queued_hash`, `latest_stored_hash`, `latest_stored_at`; after `replace_for_hash` for that hash and `finish` it returns `pending false`; a lesson with no stored doc returns all-null, `pending false` — verify: `npx vitest run packages/db/src/repos/check-queue.int.test.ts -t pending_for_states` — evidence: 3 cases — covers: R-28, CON-13
