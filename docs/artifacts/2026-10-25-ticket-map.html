1 · The story in one minute

Newsela needs about 40 lessons for each unit of its new California reading course. Today a writer drafts each one and a reviewer checks it. Our tool reads the unit's outline sheet and has Claude write every lesson. Then code checks each draft, two reviewers edit it together, and a second person approves the exact version they read.

Success is one number, the north star: reviewer minutes per approved lesson (M-1). Fewer minutes means more lessons for the same staff. A guard (M-3) catches anyone who gets there by skimming.

A ticket is one small, testable piece of that tool. The plan cut the product into 147 of them. It put them in 13 waves. A wave is a group that can be built side by side, because no ticket in it needs another from the same wave. The rest of this page shows how far each part has come.

3 · How one feature becomes tickets

Take one thing a curriculum lead does: start a run, which writes a unit's lessons. The plan splits it into three tickets, so the screen and the backend are built at the same time by different agents. They agree in advance on a contract: a written promise of what the screen sends and what the backend answers (here CON-5 in docs/contracts/INTERFACE.md).

NL-27 · Backend Merged

The backend: the code that starts a run and records it. It is tested with stand-ins ("doubles") for the parts it calls, so it never waits for the screen.

Wave 3 · depends on NL-12, NL-13

NL-58 · Screen Waiting on others

The screen: the Start run dialog. It is built against a mock server that answers exactly as the agreed contract says, so it never waits for the backend.

Wave 4 · depends on NL-24

NL-95 · Join Waiting on others

The join: the real dialog against the real backend. It runs only after both halves are merged, and re-runs the screen's checks for real.

Wave 5 · depends on NL-34, NL-58, NL-78, NL-90

Four kinds of ticket Fact

  • Backend (64): logic, storage, model calls.
  • Screen (23): one screen spec, built against the mock.
  • Join (56): a screen and its backend, wired together and re-checked. Docs, evals and delivery work sit here too.
  • Design system (4): the shared look, tokens and basic parts every screen uses.

Four lanes: who does it Fact

  • Build loop (122): plan, build, test, review, merge.
  • Direct (17): documents. One agent writes them, with no code gates.
  • You (8): only you can do it.
  • Spike (0): the three experiments already ran at Stage 5.
