The story so far

Newsela is a company that makes reading material for schools. It is moving into California's core reading and English-learner classes. That means about 180 lessons for each grade, each about 50 minutes long, each written in Newsela's own lesson shape and good enough for state reviewers. The brief asks us to build a tool that takes a designer's unit outline (a Google Sheet), has a model write the lessons, and then lets staff review, edit and approve them.

Stage 1 found that the real cost is not writing. It is the time a person spends checking each lesson. So the number we aim at (the north star, PD-1) is reviewer minutes per approved lesson. A system that writes quickly but wastes review time has missed the point.

One evening in the demo. On Sunday evening an author uploads the Grade 6 Unit 4 outline and presses Generate. The web app writes one run and 47 job rows to the database in one go and answers in well under a second. A separate worker program picks the jobs up six at a time, asks the model for one lesson per job, checks each lesson with plain code, fixes a failing one at most once, and stores it. About 25 minutes later [C on A] the board shows 47 tiles. Most say ready; a few say failed with a reason and a "retry failed" button. Meanwhile many reviewers are editing other lessons through a third program that handles live typing. Their typing never waits behind generation, because the two kinds of work run in different programs with different limits.

What earlier stages settled

  • Stage 3 found ten hard problems (HP-1…HP-10), each with a chosen option, recorded under PD-32. Orchestration (HP-1) came first. Register.
  • The interface spec has 24 cards (CON-1…CON-24), all marked agreed after the System review (DO-3 header).
  • Five foundation answers fix the load (500 users a day, a 200-user spike), the failure to survive (a worker restart mid-run), the spend ceiling ($0 new hosting, $75 for model calls), and the hardest uncertainty (can one call write a lesson?).

What changed the design after it was first drawn

  • PD-33, your load figure. It moved the target from 25 editors to a 200-user spike. That is why checks left the live-editing program (D-6) and why the 200-user load test exists.
  • SP-1. One call per lesson passes, but the API's strict-schema mode refused our lesson schema, so the schema now travels in the prompt and code validates the answer. It also set the caps: six jobs in flight, $13.00 per run, 240 seconds per call.
  • SP-2. Freezing in place beats closing every connection. The close-all rival brought refused keystrokes back (120 in 20 trials), so DO-3 now says "do not build it".
  • SP-3. The name scan cannot block everywhere on real drafts, so it blocks only in check items.
  • The code-design review (Metz). It returned FAIL with three blocking findings about build order, shared files and carrying SP-2 into the design. DO-3 and DO-4 carry the fixes now; see Reviews for what is and is not re-checked.
  • The spec dry run. An agent tried to write tests for three tickets from the design alone and found 29 gaps. All 29 are closed.

What breaks first

Predicted [A], to be confirmed by the load script (step 8):

  1. The collaboration process's single event loop carries every socket, broadcast and store. It is the only single-threaded resource every editing user shares, so it is the first to show latency (remote edit p95). Moving checks out (D-6) buys roughly 5× headroom [C on A]; step 3 of the scale path is the next fix.
  2. Postgres connections during store bursts. The store transaction is the longest hold (p95 ≤ 500 ms), so a burst of simultaneous stores is where the collaboration pool of 5 [T] could queue. Average demand is ~1.3 busy connections [C on A].
  3. Next.js server rendering on lesson open (≈ 0.33 core at the spike [C on A]); step 2 of the scale path.

On the generation side the order is: provider rate limit, then the per-run spend cap, then the worker cap. None of them touches interactive latency, because generation runs in its own process and its own pool.

The scale path

If the project later grows, nothing needs to be redesigned. Each step below is a written change, and each fires on a measurement, not a feeling.

Proposal Claude's path from the capacity doc, recorded under PD-32 PD-32. None of steps 2 to 5 is built. DO-1 §7.2.

From the capacity doc, with the measurement that fires each step:

  1. Now: one web, one worker, one collab, Postgres.
  2. Lesson open p95 > 1.5 s or web CPU > 70% at the spike → two web instances behind a proxy (stateless; sessions in Postgres).
  3. Remote edit p95 > 500 ms or collaboration event-loop lag p95 > 100 ms → a second Hocuspocus process with Postgres or Redis pub/sub fan-out, documents sharded by lesson.

  5. Whole-program runs (180 lessons per grade) → the provider's batch API for the full-unit path (HP-7 option D, roadmap), keeping the interactive path for live demos and retries.

6.2 The failure the deployment must survive (SD-7.2)

Innocent's answer (interview Q-008, 2026-10-25): a worker restart mid-run. "The run resumes at the next unfinished lesson, no lesson is stored twice, no completed call is paid for again, calls lost in flight are at most the concurrency cap and are counted." No replica or zone failure is designed for.

How the design survives it (HP-7 option B):

  1. Lease expiry. A restarted worker returns jobs whose lease lapsed to queued. On SIGTERM it stops claiming and lets in-flight calls finish.
  2. Raw-output checkpoint. A job whose model_call already holds raw output compiles from it with no second call.
  3. Idempotent store. A unique key on (run, lesson, prompt version, schema version) makes a second store a no-op.
  4. Bounded loss. Calls in flight when the process dies are paid for and lost; there are at most 6 [A], and the run summary counts them (calls_lost_in_flight, CON-21).

Failures we do not design to survive, and what happens: losing Postgres loses the project (mitigated by one pg_dump after the full run and before recording, PD-30); a collaboration restart drops sockets for ≤ 10 s with edits held locally (capacity doc recovery criteria); a web restart is invisible beyond one failed request.

SP-2 · Does freezing at Submit hold while two people type? Fact

Q-1 · Where do the checks run? Awaiting approval

Where this comes up in the project

Reviewer Mira deletes the only checking item for RL.6.6 in Lesson 4 while two colleagues type in the same lesson. Within 5 seconds the issue list must say "RL.6.6 has no checking item" (R-28), because Submit stays off while a blocking issue is open.

The problem we're solving

Decide which program runs the checks after each store: the worker (A), or the same collaboration program that carries everyone's typing (B).

Why it's hard

The collaboration program has one thread, like one cashier serving 140 people. Broadcasting keystrokes plus saving costs about 0.2 of a core. A check at the guessed 50 ms adds 0.25 and fills about 0.45; at 150 ms it adds 0.75 and fills about 0.95 [C on A]. At that point everyone's typing queues behind check runs. We do not yet know the real check time (an [A]).

Why we're asking you, and what your answer changes

Four tickets build on the answer: the check runner, the store transaction, the collab server and the issue list. If we build with B and the checks turn out slow, we rebuild the store and the pending flag in CON-13. It is cheap to change now and costly after wave 2.

A · Worker runs checks · recommended

the store writes one check_job row; the worker claims it.

If you pick it: typing is protected; about 0.5 s of claim delay; one more small table.

Tradeoff: slower by a half-second; safer under load.

B · Collab runs checks

checks run inside the collab program.

If you pick it: no queue, so the pending flag comes from memory; fewer moving parts.

Tradeoff: loses the headroom the 200-user target needs.

Decision needed: Should the checks run in the worker (A) or inside the collaboration server (B)?
