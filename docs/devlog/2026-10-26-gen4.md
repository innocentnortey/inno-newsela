# GEN-4: NL-127 capacity-run defects (F-2 stub unit_plan failure, F-4 check.failed, stored-wait split)

Naming note: the capacity report's "M-24 stored" is mislabelled. In `docs/design/metrics-registry.md` M-24 is socket reconnect time (met); stored latency is US-36 / M-19.

**Changed.** F-2: `StubModelClient` now throws `UnscriptedStubCall` (carries a fixed-enum `safe_reason`, e.g. `unscripted stub call: GENERATION/unit_plan`). `recorder.ts` gains `safe_reason(e)` (the carried reason, else the class name, never `e.message`) and uses it for non-provider errors: the failure message becomes `unexpected client error: <reason>` and the `model_call` log line gets `reason`. `claim_loop.job_failed` logs `reason` too (inlined in the worker: a lint rule keeps the worker queue off the recorder import). Tests: stub, recorder (a secret-bearing `Error` stores `Error` only), claim loop, and two `demo-stub.int` twins (scripted run leaves planning with no job running; unscripted run fails with the reason in both log lines). Stored-wait split: `LessonPersistence.note_change` + an `onChange` hook; `collab.stored` now logs `store_wait_ms` (first unsaved change to store start) and `db_write_ms` (the port call). `load/store-split.ts` aggregates them. No debounce setting touched.

**Why.** F-2 took a day to diagnose because the failure said only `unexpected client error`. The `model_call` table stores the error kind only (`ModelCallLog.fail` drops the message by design), so the reason lives in the two log lines, not a column; the plan expected it in the stored row, and that is the one deviation. The stored p95 of 6.0 s could not be split into debounce wait and database write before; now it can.

**Checked.** F-2 repro at the `demo-stub.int` level: unscripted fails with `unscripted stub call: GENERATION/unit_plan` in the `model_call` and `claim_loop.job_failed` lines; with `script_demo_stub` the run leaves Planning.
