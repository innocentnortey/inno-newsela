## Defects found (not fixed: outside this ticket's fix boundary)
1. **Finished candidate runs stay `planning`.** `derive_run_state` has no `plan_stored` for a candidate run, so `run.state` never leaves `planning`. `CLAIM_SQL` only looks at the first `MAX_ACTIVE_RUNS` (3) runs in planning/running, so after three regenerates every later job (candidate or full run) starves. The driver and `settleCandidates` close the run by SQL as a workaround (driver prints `run_state_after_job`). Owner: worker/core run-machine (A9).
2. **Candidate that becomes a lesson's v1 is reported `drafting` forever.** `PgCandidateLookup.version_of_run` only matches `kind='candidate'`, but `store_candidate` writes `kind='generated'` for a `generation_failed`/no-v1 lesson. The row, state `draft` and `current_version_id` are right; `getCandidate` and SCR-9's poll never settle. Marked by `test.fail()` in `failed_and_v1` (flips when fixed). Owner: `packages/db/src/repos/candidate-lookup.ts`.
3. `StoreAck.stored_by` is parsed as a ULID `UserId`: a user id like `usr_e2e_<hex>` makes a successful adopt return 503 `COLLAB_UNAVAILABLE` (`collab.bad_body`) after the edit was applied. Same family as the con-21 finding; tests use ULID-shaped users. The web should not report a stored edit as unavailable.
4. `model_call.request_id` is null on worker rows; correlation is by `run_id`/`job_id` only (R-48 says one correlation id).
5. SCR-9 shows no last-editor name, so "adopter shown as last editor" is asserted through `GET /api/lessons/{id}.last_editor`; four-eyes itself is NL-53's (an approver cannot also be the reviewer adopter).
